# ADR-002: Backend Authority and Order API Boundary

## Status

Accepted

## Context

The QR menu frontend runs inside the customer's browser.

Browser state, localStorage, prices, totals, product availability, and submitted values can all be modified by the customer.

Therefore, the frontend cannot be trusted as the final authority for orders.

## Decision

The backend will be the authoritative source for:

- restaurant identity,
- current menu data,
- product availability,
- final product prices,
- final order totals,
- order IDs and order numbers,
- order status,
- persisted order history.

The frontend will be responsible for:

- displaying the menu,
- maintaining the temporary customer cart,
- keeping the cart across page reloads,
- collecting quantities,
- showing price snapshots,
- submitting order requests,
- displaying server validation results.

## Order Submission

The frontend may send:

- restaurant identifier,
- product IDs,
- quantities,
- price snapshots observed by the customer,
- an idempotency key.

The backend must never calculate the final order using prices supplied by the browser.

For every order attempt, the backend must:

1. Validate the restaurant.
2. Validate every product ID.
3. Confirm every product is available.
4. Validate quantities.
5. Load current prices from the database.
6. Recalculate every line total.
7. Recalculate the complete order total.
8. Compare trusted prices with customer price snapshots.
9. Create the order only if validation succeeds.

## Price Changes

If a price changed since the customer added the item to the cart:

- the order must not be created silently,
- the backend returns a price-change result,
- the frontend displays the updated price,
- the customer confirms again.

The trusted backend price always wins.

## Unavailable Products

If a product becomes unavailable:

- the order is not created,
- the backend returns the unavailable product IDs,
- the frontend informs the customer and updates the cart.

## Idempotency

Every checkout attempt must include an idempotency key generated by the client.

The backend must prevent the same checkout attempt from creating duplicate orders.

This protects against:

- double clicking,
- slow mobile networks,
- retries,
- repeated HTTP requests.

## Order Snapshot

After successful validation, the persisted order stores its own snapshot:

- product ID,
- product name,
- trusted unit price,
- quantity,
- line total.

Historical orders must not change when menu products or prices change later.

## Public Customer API Boundary

Initial customer-facing API responsibilities:

GET /api/v1/menu/:restaurantSlug

Returns the current restaurant and menu.

POST /api/v1/orders

Validates trusted menu data and creates an order.

GET /api/v1/orders/:orderId

Returns the customer's order status when appropriate.

Admin APIs are a separate boundary and will require authentication.

## Security Rules

All external input is untrusted.

The backend must validate:

- IDs,
- quantities,
- strings,
- request shapes,
- restaurant ownership relationships.

Secrets and database credentials must never be exposed to the frontend.

## Non-Goals

This decision does not yet define:

- payment processing,
- customer accounts,
- loyalty,
- inventory,
- POS integration,
- promotions,
- advanced delivery logic.

These are intentionally deferred.

## Consequences

The frontend becomes a client of the backend rather than the source of business truth.

LocalStorage remains useful for customer experience but has no authority over final pricing or order creation.

Order creation becomes secure enough to later support real restaurant usage.

## Revisit Trigger

Review this decision if we later add:

- online payments,
- POS integration,
- complex branches,
- promotions,
- delivery fees,
- taxes,
- customer accounts.
